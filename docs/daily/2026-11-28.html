In-browser inference trades prompt speed for locality

An experimental WebAssembly engine approaches native generation speed on one machine while lagging badly on prompt processing.

Tesseracted describes an experimental terminal that runs Qwen-family models entirely in a browser tab: weights download once into cache and a roughly 52 KB WebAssembly module computes every token on the CPU, with no GPU code or inference API. A bare-metal LLM runtime credits its speed to removing Linux

A 24 KB assembly OS claims up to 54% faster token generation than llama.cpp, as a single-author demonstration of one small model.

A developer reports baking a Qwen3-0.6B model into a 24,252-byte pure x86-64 assembly operating system that boots in 74 to 94 milliseconds and chats over VGA, keyboard and serial, with no Linux, C, Rust or libc underneath. Self-reported benchmarks on the same AMD EPYC 7642 claim 23.67 versus 16.63 tokens per second at one thread against llama.cpp, rising to 134.94 versus 103.03 at sixteen threads, with bit-exact output across thread counts and 0.99965 cosine similarity against PyTorch FP32. A diskless 2 GiB Proxmox VM reportedly boots to a prompt in under five seconds and decodes at 78 tokens per second. These are single-author measurements posted on X with a repository link; no independent reproduction, and the gains apply to one small quantized model rather than general LLM serving. (read more).

Agentic work moves the effort to planning and review

An experience report and a new multi-machine framework both assume agents work unattended, guarded by sandboxes, rules and pipelines rather than constant supervision.

Ivan Kahl argues that letting AI agents code while you walk away is workable only if effort moves from supervising every step to planning up front and reviewing the finished pull request. His workflow: decide the architecture yourself and record decisions in ADRs, have the agent propose a task breakdown and refine it, slice work vertically so each task is testable, then let the agent implement in a sandbox while pipelines and an AI review check the result. Safety comes from rules that do not fade: branch protection, required reviews, secret scanning and a sandbox that assumes a hijacked agent, with no production credentials and a restricted network. He warns agents can be steered by text they read and can optimize for a green pipeline rather than correct behavior, so tests need protection too. This is a single author's experience report, not a controlled comparison, and its examples are one .NET codebase. (read more).

Fleetlayer is a source-available, early-stage framework for running many Claude Code and Codex agents across several machines and accounts. A small node on each machine keeps one outbound connection to a control plane, so it works behind NAT; agents can message each other, share a signed-in browser through Playwright MCP, and act under per-user rules, such as an agent that reads strangers' email being allowed to message only its owner. A dashboard shows every machine, session, pending approval and event. The project explicitly targets the second-machine, second-account case and tells single-laptop users to stay with Claude Code's own features. These are vendor claims on a product page: the access-rule enforcement, account handling and security properties are unaudited, and nothing here was installed or tested. (read more).
