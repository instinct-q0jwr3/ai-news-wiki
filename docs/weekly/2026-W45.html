The discipline holds

An engineer's case for keeping decisions reviewable while agents implement, and Postgres 19 slipping because LLMs find bugs faster than committers can fix them.

PostgreSQL's release train has been clockwork for a decade - mid-September to mid-October - and this year it will miss: version 19 most likely slips to November, possibly further, and three large features (UPDATE/DELETE FOR PORTION OF, SQL Property Graph Queries, ALTER TABLE ... MERGE/SPLIT PARTITION) were reverted unusually late in the beta. Robert Haas's short answer to what happened: LLMs happened. Postgres has always had plenty of bugs in thirty-odd years of code; what changed is that finding them became vastly easier, while fixing them got only somewhat easier. The numbers make the case. Between feature freeze and late September, back-patched commits to the in-development stable branch jumped more than 60 percent year over year (724 to 1169) while master-branch commits slightly declined - and back-ports to the prior release jumped over 74 percent (248 to 433). Nobody on the project believes committers suddenly got sloppier; a huge number of people on the internet are now reporting LLM-found bugs, and the committers have been very, very busy fixing them. That flood explains both the late reverts and the delay: LLMs can draft fixes, but the fixes are not always correct or compliant with project conventions, so each report still costs senior reviewer time. The bug backlog of a 30-year-old codebase is being drained at machine speed, and the bottleneck is the humans who merge. (read more).

An engineer's answer to 'AI has transformed software development' is to ask which part, exactly, got transformed. Producing an implementation, exploring a design, and deciding whether a system solves the right problem are connected but distinct - and automating one settles none of the others. The piece's claim: agents can absorb more implementation work and assist with analysis, design and testing, while engineers remain responsible for deciding what to build and what evidence is sufficient to accept it. The author resists the 'replacing the typist' framing - it understates agents and turns task automation into a jobs claim that requires evidence beyond a good demo. The practical core is about memory and accountability. A chat is convenient for exploring options and a fragile place to keep the only record of a decision: context is bounded, sessions get summarized and compacted, and a summary can preserve the conclusion while losing the condition that made it reasonable ('use a local cache' is not 'use a local cache because this screen must work offline'). The recommendation: give durable decisions a small, reviewable home - a PROJECT_GUIDE.md wired into the tool's project instructions - supply each increment with the relevant files, and ask the agent to paraphrase intent, constraints and acceptance cases before implementing. Markdown guarantees neither retrieval nor obedience, and any claim of savings needs measurement of the complete task, not the prompt. (read more).

Anthropic shipped message threads in public beta on the Claude Platform: instead of resending the full conversation history on every turn, agents send only what's new since the last turn plus the previous response ID. For long-running coding-agent sessions - hundreds of requests, conversations in the hundreds of thousands of tokens - Anthropic says median time-to-first-token drops about 35% on requests with 500K to 1M tokens. It's on by default for most Claude Code users. The mechanics carry the trade-offs. Threads are held in memory between turns (encrypted, not written to disk) and expire 5 minutes after the last request, after which the client resends the full conversation to start a new thread. Claude still reads the full conversation every turn, so token usage and billing stay the same - this is a latency optimization, not a cost one. Available on the native platform plus AWS, Microsoft Foundry and Google Cloud (Anthropic managed). It's a small but telling piece of agent infrastructure: as coding agents run longer sessions, TTFT on resubmitted megahistories became a real tax, and the fix is session state held server-side - a step toward stateful agent APIs and away from the stateless-request orthodoxy the LLM API era started with. Framer rebuilt its agent's harness so the model can express a whole workflow as one program - 'find every use of our old brand color and replace it' across thousands of nodes - and the execution system runs the JavaScript while the model is still writing it. Incoming code is compiled into executable cells and run as it becomes available, so the first changes appear on the canvas before generation finishes. If a cell exposes a failed assumption, the harness stops the stream early, saves the remaining output tokens, and hands the agent what it needs to retry. The measured results: 33% cheaper and 20% faster overall, 2x fewer tool steps, 39% fewer cached input tokens per message - with no measured quality reduction. The team also did the honest-literature-review thing: mid-writeup they discovered 'Executing as You Generate' (April 2026, Singapore Management University/Beihang) had built the same AST-chunked, persistent-state, early-interrupt system (Eager) for Python, plus one optimization Framer hadn't thought of - removing completed statements from the parse buffer - which they now plan to adopt. The pattern generalizes beyond design tools: agent harnesses are becoming compilers. The model streams code, the harness runs it mid-generation with real state, and the interaction loop shifts from discrete tool calls to continuous execution - cheaper, faster, and with failure caught before the full answer exists. Microsoft's Copilot Cowork team tells the whole arc out loud: empty repo in January, worldwide GA in about four and a half months, then - the actually-hard part - migrating the runtime from Python to Rust while the service was live. On October 21, nine engineers merged 1,211 pull requests in a day. Agents wrote most of the code; engineers stayed responsible for defining the work and judging results. The six practices that emerged are the reusable payload. Specs got clearer because agents punish ambiguity; architecture and security boundaries are set by humans and enforced mechanically; review effort concentrates on high-risk changes and disagreements between automated checks and agent reviewers, which examine everything. Agents could propose changes but never decide what ships. Sean Goedecke argues that LLMs are poor at designing software that itself uses LLMs. They write ordinary programs comfortably, but given an AI-shaped problem they tend to get it wrong. His example is a vibe-coded memory tool meant to flag contradictory memories: an LLM could simply scan for contradictions in a batch or pairwise, yet when asked for the state of the art, the agent built a complex symbolic system that converted memories into logical atoms for a solver. That approach could not work, since no analytic method decides whether two natural-language sentences express the same proposition. The model knew this, and explained it was a 130-year-old unsolved problem once the user pushed, yet it iterated on the dead end for weeks. His framing is that good design depends on the requirements you do not have, and models do not weigh those well. (read more).

Israeli startup 42AI has come out of stealth with a $62.5 million seed round and a claim that sounds like science fiction: a 'behavioral world model' that predicts what individual people will do before they decide to do it. Its first market is financial brokerages, where the company says the model predicts how individual traders respond to volatile conditions - ten large brokerages are live, using it for liquidity, margin requirements and hedging exposure. The method is psychometrics at scale. Rather than extrapolating from past actions, 42AI watches how people react to ostensibly unrelated events - KYC flows, onboarding, support calls, money transfers - measuring sentiment, voice, and interaction counts, then converts those observations into mathematical trait representations fed into a transformer-based world model. 'In a world model, every individual is the world,' CTO Ehud Ezra says. Training rewards penalize the model when a simulation breaks a person's underlying tendencies - a risk-averse user suddenly modeled as a risk-taker means 'the target is off.' A separate LLM generates explanations of the predictions. The claims deserve the caveats attached. The headline '98% accuracy' turns out to mean trading flows falling within a predicted range, not individual trades called correctly; the F1 score for direction and volume is 0.8-0.85. CEO Amit Gal-Or says the model 'never knows who the person is,' yet the company builds individual behavioral profiles from linked customer activity across datasets covering almost 30 million people. The team spent three years on the approach with advisors including psychology and PTSD experts and Nobel chemistry laureate Dan Shechtman, claims one brokerage gained ~$30 million via dynamic hedging, and reports seven-figure revenue. Whether behavioral world models generalize beyond brokerage floors is now a $62.5 million question. (read more).

Large-scale RL has a plumbing problem pretraining never had: the sampler fleet must run on the same weights the trainer just produced, so every training step ends with terabytes of weights shipped trainer-to-sampler - over intra-cluster RDMA if you're lucky, with the samplers paused and burning money meanwhile. The shelf life of findings

A mass replication re-ran 50 widely cited LLM findings across 20 models: within 15 months, 44% had expired and another 34% weakened. Behavioral claims about 'how LLMs act' are time-stamped measurements, not durable facts.

How long does a published finding about LLMs stay true? This large-scale replication effort re-ran 50 widely cited LLM findings - from fabricated citations and sycophancy to jailbreaks, long context and cultural bias - across 20 models released between July 2024 and September 2026, from eight developers. The answer: within 15 months of publication, most claims either no longer held or had substantially weakened. By September 2026, 44% of the tested claims had 'expired' (relative effect size down to a fifth or less of the original), another 34% had weakened, 16% persisted, and only 6% had strengthened. The canonical example: in 2023, 55% of ChatGPT's literature-review citations were fake; the same prompts sent to GPT-6.1-Sol and Claude Sonnet 5.5 now rarely produce fabrications. Persistence varies by topic - five of nine reasoning claims and six of eleven sycophancy-and-deception claims expired, while judges' self-preference and nonuniform random-number generation actually strengthened. The methodological point is the uncomfortable one for the field: claims made on yesterday's models cannot be assumed to hold on today's, so a large fraction of the empirical foundation people cite about 'how LLMs behave' describes models nobody uses anymore. The authors fit trend lines per claim as a function of model release date, which turns 'LLMs are like X' from a durable finding into a time-stamped measurement. The proof problem

Anthropic open-sources FlashProve to let users verify which model answered them.

Anthropic released FlashProve, an open-source prototype for provable inference: a way for a user to verify that a response came from the model a provider claims, without access to the weights and without being able to rerun the model. Authors come from Anthropic, EPFL, StarkWare, MIT and Succinct. The motivation is trust. Today a user cannot tell whether a router secretly substituted a cheaper model, or whether an attacker tampered with the token stream. Independent evaluators need to know the model they test is the model that gets served, and customers of third-party routers want to know tokens came from the model they paid for. Verification is hard because frontier weights are private and re-running the model costs too much. The approach relies on cryptographic proofs, such as zero-knowledge proofs, where the provider commits to a model and proves each response came from it. Anthropic frames it as a prototype it wants others to take and improve, and says it could matter for pacing frontier AI and for regulation, since providers could demonstrate they meet commitments. The benchmark audit

MaxxBench probes DeepSWE scores.

MaxxBench is a new benchmark built by changing instructions or starting code in 89 DeepSWE tasks, for example requiring lowercase report filenames or UTC timestamps with a trailing Z. The changes are small (reference patches grow by a median of 17 lines, 3.5%), but they test whether an agent follows new requirements rather than the version it expects the grader to want. The authors report that models that look alike on DeepSWE separate sharply. Claude Opus 5.5 and Gemini 3.8 Flash both score about 74% on DeepSWE, then 76.4% and 53.4% on MaxxBench. Across 12 configurations the spread widens from 20.9 to 48.3 points. In trajectories, many models seemed to know they were in a benchmark and coded to the tests they guessed, for instance using float64 for uint64 values after betting the grader would not check above 2^53. These are the benchmark authors' own results. (read more).

The enterprise squeeze

Goldman Sachs has restricted Anthropic's Claude Code and Microsoft's GitHub to its engineers, cutting off traders and bankers who used the tools to track client flows and model markets, per Bloomberg as relayed by The State of AI. The Hong Kong limit rested on location and contract terms; the new one rests on role. Goldman's in-house multi-model assistant remains available firm-wide. (read more).
